# Boat5 两款船型：材质与彩色发光方案

日期：2026-10-21。范围：Mac v1.5.4 / build 2993 的原程序集、序列化资源和已有扩展源码，只读离线调查。**本轮没有实装、启动游戏、访问个人存档、修改 Contents、提交或推送。** Blender 的幽绿眼徽和青色灯带仍是美术预览。

后续状态（同日）：用户已确认原灯统一控制，推荐的槽 1 两纹理 MPB 路线已接入 `2.3.0-preview.3` 的新 R2 隔离副本，并通过离线测试及实际打包资源身份核验；尚未启动游戏。实现与当前验收以 [船型外观 MVP 最后交付节](船型外观MVP.md) 为准。下面保留调查当时“推断/未实施”的时间边界，不将接入或 Blender 渲染写成原 Shader 实机通过。

## 结论

- **已验证（原资源与 Metal 代码）：发光颜色来自 RGB 贴图，不是全船唯一发光颜色。** 窗、眼徽、青灯、紫色小标记可共用槽 1，通过不同 UV 采不同颜色。原贴图只提供暖色，保留原贴图而仅换网格/UV，无法直接得到这些新颜色。
- **推断（建议方案，未实施）：最小改动是两槽不变，槽 0 继续船漆，槽 1 使用配套的原创 Albedo/Emission 小图集，由该 Renderer 的槽 1 MaterialPropertyBlock 覆盖两张纹理。** 不需要改原共享 Material、增加槽或新 Shader；是否在本版本真实渲染正确，仍须将来的授权隔离实机验证。
- **已验证（代码限制）：颜色可以分区，动态强度和开关仍共用 `_LightStrength`。** 眼徽/灯带随原船灯开关及原生闪烁强度变化。若要求“原窗熄灭、眼徽仍独立常亮”，这条最小路线不满足，需要另行改变绘制/Shader 合同。

|---|---|---|
| Boat5 Renderer | MeshRenderer path ID `-3468682762928022503`，GameObject `Boat5`，材质数组按顺序为以下两项 | 本轮 `boat5-renderer-static.json` |
| 槽 0 | `Boat5_Mat`，path ID `9056148573309277135`；Shader `Shader Graphs/LitBoat_Shader`，同 CAB 的 Shader ID `-3388620609851746346` | `player-materials-static.json`；原 `player_assets_all_aa53fb6d97843ab38da4bba4ff0c59f9.bundle` |
| 槽 1 | `BoatWindows_Mat`，path ID `-2084018538323612598`；Shader `Shader Graphs/Lit_Shader`，外部 Shader ID `-9048223811437939208` | `window-shader-static.json`；Shader 位于 `itemdata_assets_all_361119de156c00019990c64b36819e44.bundle` 的 `CAB-fbbc8ff78271a5a8c4cb09c6241d8159` |

**已验证（Metal 片段）：槽 0 基色计算**为 Albedo ×（ColorMask.G × `_Hull_Color` + ColorMask.R × `_Roof_Color` + ColorMask.B × `_Base_Color`），之后进入原光照/雾处理。当前 Boat5 的 Albedo 实际引用 `Boat1_Texture` 16×16，ColorMask 为 `UpgradeBoat_Mask` 16×16，仅红/绿/蓝三种区。仅在 Blender 分配多种预览材质，不会自动变成原生船漆兼容的游戏材质。依据：`boat-fragment-unlit.metal.txt:142–147`、`native-textures-static.json`。

**已验证（REA 托管 IL）：`PlayerColorCustomizer.RefreshBoatColors`** 获取船顶/船壳颜色索引，闭包 `<RefreshBoatColors>b__0`（`0x0600213b`）对 `meshRenderer.materials[0]` 分别 `SetColor("_Roof_Color", …)`、`SetColor("_Hull_Color", …)`；`b__1` 对彩旗串同样处理。`OnBoatColorChanged`、`OnUpgradesChanged`、`OnEnable` 会触发刷新。原版已经使用实例化的 `materials` 访问；扩展不应把这些写入改为共享材质写入。依据：REA M1/M3，已有反编译 `research/decompiled/PlayerColorCustomizer.cs`。

**已验证（扩展源码）：`RendererOverrides.ApplyPalette` / `ApplyFlag`** 只在槽 0 的 MaterialPropertyBlock 上读改写船壳、船顶颜色及旗图纹理；不会主动改槽 1。`Boat5Binding` 当前只拥有网格引用，构造检查 `sharedMaterials.Length == 2` 及槽 0 的船漆属性、槽 1 的 `_LightStrength`；`Boat5MeshFactory.Create` 创建两组索引。建议方案需要增加独立的纹理覆盖所有权/释放逻辑，不能假称当前网格 MVP 已有此功能。

## 发光控制链与准确限制

**已验证（原 Shader）：槽 1 有下列有效属性：**

| 属性名 | 原 Shader 描述 | 原 BoatWindows 绑定 |
|---|---|---|
| `Texture2D_9aa7ba2263944b48bbf43c218dc48459` | Albedo | `SmallBoat_Texture`，32×32，ID `-8883912178499157096` |
| `Texture2D_c7b8c5c57d6443a5a9f86b68269754f3` | Emission | `SmallBoat_Emission`，32×32，ID `4483575173994274378` |
| `_LightStrength` | LightStrength | 单个 float，原序列化值 0，Shader 默认值 4 |
| `BOOLEAN_0965F30455D645A4AD7F01AF266AE935` | Emissive | 原 Material 已启用对应 `_ON` keyword |

**已验证（实际 Metal 程序）：**发光片段在 `windows-fragment-emissive.metal.txt:201` 用 `input.INTERP2.xy` 采 Emission 的 RGB，在第 242 行执行等价于 `output.rgb = emission.rgb * _LightStrength + shadedAlbedo` 的运算；Albedo 同样使用此 UV。两次采样都取 `.xyz`，未用采样 Alpha；片段最终把输出 Alpha 设为 1。所读取的 vertex 输入为 POSITION、NORMAL、TEXCOORD0，没有顶点颜色输入。由此不能靠 Mesh 顶点色把暖窗任意染成青灯。该代码是原包内 Metal 程序的文本，不是重写或实际 GPU 运行证据。

**已验证（原贴图像素）：**`SmallBoat_Emission` 共有 960 黑像素、32 个 `(175,164,93)`、16 个 `(98,81,61)`、16 个 `(137,122,88)`；没有幽绿、青蓝或紫红色。图集通过 UV 可支持多色，但**原图集没有所需颜色**。因此“保持原两张纹理字节不变，只重新挑 UV”无法准确复现这两款彩色发光。

**已验证（反例排除）：**材质序列化 `m_SavedProperties` 虽残留 `_EmissionColor`，但两个 Shader 的解析属性表没有这个属性；窗口的 180 个 Metal fragment 中没有 `_EmissionColor` uniform，80 个含发光采样的片段同时使用 `_LightStrength`。不能照搬 Standard Shader 的 `_EmissionColor` 方案，也不能由保存字段存在就声称 Shader 在用它。依据：`window-shader-static.json`、`window-fragment-coverage.json`。

**已验证（REA 托管 IL）：**`BoatModelProxy.SetLightStrength(float)`（`0x06000d45`）对 `boatMeshRenderer.materials[1]` 写 `_LightStrength`，同时对独立灯具的槽 0 写同名值。`LightAbility.DoActivate`（`0x06000d0e`）传 4，`Deactivate`（`0x06000d0f`）和销毁路径传 0；`LightFlickerEffect.Update`（`0x06001b82`）也调用此方法。窗口与新增发光几何共用槽 1 时会一起响应它，不能给不同三角形分别设这个统一 float。依据：REA M1/M2/M3。

**推断（明确能力边界）：**图集中不同 RGB/亮度可给出固定的相对强弱，仍不是独立动态开关。单独用槽 1 的 PropertyBlock 强制 `_LightStrength` 常量，会同时影响窗面并压住上述原生灯效，不作为推荐方案。Shader 自发光也不等于新增照亮海面、甲板的真实灯光；没有必要为纯外观新增 Light。

**已验证（有界冲突核查）：**复用 M1 已解码的原 `Assembly-CSharp.dll` 全部 2,856 个 MemberRef，分六页精确检查 `MaterialPropertyBlock`、`GetPropertyBlock`、`SetPropertyBlock` 名称，未见匹配；`rea-mpb-reference-check.json` 保存每页 Evidence ID 和穷尽页边界。现有相关反编译文件也未见这些调用；扩展 `RendererOverrides` 的实际调用限定槽 0。这个结论只覆盖该程序集的静态直接引用，**不等于其他 DLL、反射、Unity 原生内部或未来模组不会写 block**；尚未证明真实槽 1 没有其他写入者。MPB 与原灯强度、slot0 油漆匠共存仍列入未来隔离 GPU 验证，不再扩大扫描。

## 推荐路线与备选代价

1. **推断，推荐：保留 Renderer、原两槽和原 Material 对象；只增加槽 1 两张原创纹理的 PropertyBlock 覆盖。** 窗户使用保留暖色的图集格，眼徽/灯带使用幽绿/青/少量紫的格；Albedo/Emission 的分区必须完全配对，因为它们采同一 UV。四伤态保持同一套语义/UV。槽 0 先沿用原颜色遮罩与船漆规则，不覆盖油漆匠的槽 0 block。新增图集要有边缘留白、明确采样/色彩空间设置，避免小格在 mip/过滤时串色。此方案目前仅由 Shader 与现有 MPB 接缝支持，**未制作游戏纹理、未调用游戏 API、未验证运行**。
2. **推断，只有需改 keyword/材质状态时才考虑独立 Material 实例。** 复制原槽 1 材质后沿用同 Shader/属性，仍可保留两个槽、不修改原共享资源，但要备份原数组引用并在换档/恢复/场景重建时先还原再销毁实例。它仍只有一个 `_LightStrength`，本身不能解决眼徽独立常亮；不应仅为换纹理就增加这层所有权。
3. **推断，独立常亮才需扩合同：**另一个受控绘制路径，或带“窗/装饰发光分区 + 两路强度”输入的自定义 Shader。多一个材质槽会直接违反当前 `Boat5Binding`/两子网格检查，并增加资源、draw call 与恢复负担；单独 Renderer 可保留原 Renderer 的两槽，但须管理新对象、四态同步及清理，也超出现有只换 `damageStateMeshes` 合同。自定义 Shader 必须另证本机 Metal/URP、原雾/海浪遮罩/光照与船漆兼容，不能把 Blender 发光材质直接拷进去。当前**未验证**，不推荐作为第一条实装路线。

**推断（恢复要求）：**纹理覆盖也必须有独立备份和所有权检查。读取槽 1 原 block/纹理基线，只回退本功能拥有的属性；不要 `Clear()` 整个 Renderer block，不覆盖槽 0，也不要把 `_LightStrength` 恢复成某次缓存值，因为原灯开关仍拥有它。若其他写入者已接管槽 1，恢复需保留其新值。先解除新纹理引用再释放资源；切档、场景重建和恢复原版都走同一释放路径。视觉恢复到原版与 block 内部字节完全一致是两种证明，应分别说明。
